# Initial changes to TightVNC 2.8.90

Notes on the first round of work on this fork (October 2026): what was
changed, why, and what was considered and left for later. Commit hashes
refer to this repository.

## Goal

A modernized build of the TightVNC **viewer** for Windows 10/11, used
mainly as a view-only monitor over a LAN with a wayvnc server. The
deliverable is the single statically linked `x64\Release\tvnviewer.exe`;
the installer is not used.

## Base

The base is the official TightVNC 2.8.90 GPL source zip
(`tightvnc-2.8.90-src-gpl.zip`, SHA-256 `f3f76393…061c`), imported
unmodified in `da0e25d`. 2.8.90 includes the viewer decoder hardening
against malicious servers that 2.8.81 lacks.

Rejected alternatives:

- **chenall/tightvnc** (a third-party GitHub fork): its viewer is identical
  to official 2.8.81, and its server changes hardcode a default password
  and disable password deletion.
- **TigerVNC**: pinned to FLTK 1.3, no DPI awareness, FLTK file chooser,
  and its H.264 decoding did not work with wayvnc.

## Build

Requirements: Visual Studio 2026 (toolset v145) with the Windows 10/11
SDK and the vcpkg that ships with Visual Studio (or a standalone vcpkg in
`VCPKG_ROOT`).

```
MSBuild SquirrelVNC.slnx /p:Configuration=Release /p:Platform=x64
MSBuild SquirrelVNC.slnx /p:Configuration=Release /p:Platform=Win32
```

The 32-bit platform is named `Win32`. Only Debug and Release
configurations exist, both Unicode.

vcpkg runs automatically during the build (manifest mode) and installs
into `vcpkg_installed/`. If a vcpkg download falls back to another
mirror, vcpkg prints the fallback as `error:` lines, which MSBuild counts
as errors; the next build then succeeds because the download is cached.

### Dependencies from vcpkg (`2a5f02e`, `fcdcf83`)

- `vcpkg.json` lists `libjpeg-turbo` and `zlib-ng`.
  `vcpkg-configuration.json` pins the registry baseline
  (`1460b31b08c42cc2e9ac2c79f45ec8707e2675e2`) and adds the overlay
  triplets in `triplets/`.
- `Directory.Build.props` and `Directory.Build.targets` import vcpkg's
  MSBuild integration from `VCPKG_ROOT` if set, otherwise from
  `$(VsInstallRoot)\VC\vcpkg`, so no `vcpkg integrate install` is needed.
  `VcpkgUseStatic` selects the `x64-windows-static` /
  `x86-windows-static` triplets, matching the static CRT (`/MT`) the
  projects use.
- `triplets/x64-windows-static.cmake` and `x86-windows-static.cmake` are
  copies of vcpkg's built-in triplets that additionally build zlib-ng with
  `ZLIB_COMPAT`, so it provides `zlib.h` and the standard zlib API.
- Sources now include `<jpeglib.h>` (`viewer-core/JpegDecompressor.h`,
  `rfb-sconn/JpegCompressor.h`) and `<zlib.h>` (`util/ZLibBase.h`,
  `rfb-sconn/TightEncoder.h`). The bundled `libjpeg/` and `zlib/`
  projects were removed.
- zlib-ng was chosen over Cloudflare's zlib fork: Cloudflare's is not in
  vcpkg, and its gains are mostly in compression (server side); TurboVNC
  issue #95 measured only about 1% faster decompression.

## Feature branches

`keep-display-on` is based on `main`; `dpi-aware` is based on
`keep-display-on`. Both have been built and tested on Windows 10 LTSC.

### `keep-display-on`

Keeps the local display on, and so prevents the screen saver and the
lock screen, while a view-only connection is open. This replaces running
PowerToys Awake alongside the viewer.

- `2956cbc`: `util/winhdr.h` raises `WINVER`/`_WIN32_WINNT` from 0x0501
  (Windows XP) to 0x0A00 (Windows 10), needed for the power request API.
  Compiler warnings were unchanged.
- `cb0082b`: new class `win-system/DisplayRequest` wraps
  `PowerCreateRequest` + `PowerSetRequest(PowerRequestDisplayRequired)`,
  with `activate(reason)`, `deactivate()` and `isActive()`, guarded by a
  `LocalMutex`. `ViewerWindow` holds one as `m_displayRequest`:
  - `ViewerWindow::wantsDisplayKeptOn()` decides whether the display
    should stay on. It currently returns `m_conConf->isViewOnly()`; this
    is the place to plug in a separate connection option later.
  - `ViewerWindow::updateDisplayRequest()` activates or clears the
    request to match the connection state, and is called at the end of
    `applySettings()`, so toggling view-only mode takes effect at once.
  - `onDestroy()` clears the request.
  - The reason string is the window title (`formatWindowName()`), shown
    by `powercfg /requests` under DISPLAY.

### `dpi-aware`

- `2c7583e`: `tvnviewer/tvnviewer.vcxproj` sets
  `<Manifest><EnableDpiAwareness>true</EnableDpiAwareness></Manifest>`
  for all four configurations, so the embedded manifest declares the
  viewer **system DPI aware**. Previously the viewer had no DPI
  declaration (unlike the server, which has `tvnserver/DPIAware.manifest`)
  and Windows bitmap-stretched it, so the text and remote desktop were
  blurry at scaling above 100%.
- Dialogs use `MS Shell Dlg` and dialog units, so they scale correctly.
  Bitmaps do not: they are drawn at their native pixel size and now look
  small at higher scaling (see below).

## Findings and possible follow-ups

### Artwork at high DPI

- Toolbar: `res/toolbar.bmp`, 256×16 at 4 bpp (16 icons of 16×16).
- Login dialog logo: `IDB_LOGO_48` = `res/tightvnc48.bmp`, 48×48 in a
  32×30 DLU box. That box is about 48 px at 96 DPI, so the logo fills it
  only at 100% scaling.
- About dialog logo: `IDB_LOGO_BIG` = `res/tightvnc.bmp`, 90×90 in a
  60×55 DLU box.
- Application icon: `res/appicon.ico` contains only 16×16 and 32×32 at
  4 bpp.

Options considered, all without run-time third-party libraries:

1. SVG sources in the repository, rendered at build time to multi-size
   ICO/PNG resources, loaded at run time at the size matching the DPI
   (`LoadIconWithScaleDown`, image lists built at the right size).
   Recommended.
2. Direct2D's SVG renderer (`ID2D1DeviceContext5::CreateSvgDocument`,
   Windows 10 1703+), drawing into bitmaps at the needed size. Fully
   scalable, but adds COM/Direct2D code and supports only part of SVG.
3. The Segoe MDL2 Assets icon font (built into Windows 10; Segoe Fluent
   Icons is Windows 11 only), drawn with GDI or DirectWrite.

### Per-monitor DPI awareness

Per-monitor v2 awareness would need `WM_DPICHANGED` handling and
rebuilding the toolbar images at the new size. It fits naturally with
option 1 above.

### Continuous updates and fences

The viewer uses the classic request/response update loop
(`viewer-core/RemoteViewerCore.cpp`, around line 1064) and supports
neither the ContinuousUpdates nor the Fence extension.
`UpdateRequestSender` is dead code, since `deferUpdateRequests()` is
never called. neatvnc (used by wayvnc) supports both and uses fences to
measure round-trip time and throttle bandwidth. Implementing them would
mean advertising pseudo-encodings −313 and −312, echoing fences, handling
EnableContinuousUpdates/EndOfContinuousUpdates, and pausing continuous
updates while the pixel format changes. Latency effects can be tested
with `tc netem` on the server side.

### JPEG decoding

`JpegDecompressor` decodes to `JCS_RGB` row by row and converts to the
frame buffer format in a separate pass. libjpeg-turbo can decode
directly to `JCS_EXT_BGRX` (as TigerVNC does), or the TurboJPEG API can
be used, avoiding the extra pass.

### Possible later work

- A separate "keep display on" connection option (see
