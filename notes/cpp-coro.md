## [2026-10-22] Eliding heap allocations of coroutine frames

<query>

### User's query

I have a question about the implementation of C++20 coroutines.

I'm planning the migration of a old C++ codebase, that today reads and writes from the non-blocking sockets with multiple threads, to use a single event loop driven by a dedicated thread that handles all network reads and writes.  I want to assess the impact of efficiency before starting any work.

The parsing of the network protocol is complicated enough, so the coroutines would indeed become ‘viral’ (function coloring) across many functions.

The functions today are implemented in separately-compiled `.cpp` files.

In the C/C++ ABI for traditional (non-coroutine) functions, the stack is assumed to be sufficiently large so whatever local variables each function wants to use can be allocated without the knowledge of the caller.

With coroutines, if the target function suspends, it needs somewhere to spill the local variables that it needs to across suspension points.  The most straightforward to implement that would be for each coroutine frame to be allocated with `new` or `std::malloc`.  But it would not be efficient if there is a deep call chain of coroutine functions and the last one suspends.

And as far as I know, coroutines cannot communicate their required frame layout parameters across the ABI boundary.  It runs into the chicken-and-egg problem where the internal type of the frame is compiler-generated but would somehow need to be surfaced to the API as a sized type if separate compilation is to be supported.

So, I think that leaves the problem to be solved with “whole-program optimization” / “link-time optimization”.

My question is then, do compilers do that?  The one I'm primarily working with is MSVC, and in the future Clang (MSVC ABI; once the codebase / build system is ported to use that compiler also).
</query>

<response>

### AI's response: introduction

Yes, compilers absolutely do solve this via Whole-Program Optimization (WPO) and Link-Time Optimization (LTO). What you are describing is a well-known optimization called **Heap Allocation Elision Optimization (HALO)** or simply Coroutine Elision.

You have correctly identified the fundamental ABI limitation: because the coroutine frame size and layout are generated by the compiler and are not part of the function signature, a standard cross-translation-unit (TU) call has no way to know how much stack space to reserve. Without cross-TU visibility, the compiler is forced to fall back to heap allocation (`operator new`) for every frame in the call chain.

Here is how MSVC and Clang handle this when WPO/LTO is enabled.

### 1. How the Compilers Handle Coroutine Elision

For the compiler to elide the heap allocation and put the coroutine state on the caller's stack (or inline it completely), it must prove two things:
1.  **Visibility:** The compiler must see the exact size of the callee's coroutine frame.
2.  **Strict Lifetimes:** The compiler must prove that the lifetime of the callee's coroutine frame is strictly nested within the caller's frame (which is inherently true for standard `co_await` chains where the caller waits for the callee to finish).

**Clang (LLVM)**
Clang relies heavily on its `CoroElide` optimization pass. When you compile with LTO (`-flto` or `-flto=thin`), the LLVM intermediate representation (IR) of your separate `.cpp` files is merged at link time. LLVM's coroutine passes run *after* this merge. This gives `CoroElide` the cross-TU visibility it needs to determine the frame sizes of your nested network parsing functions and allocate them on the caller's stack. LLVM is currently considered the industry leader in aggressive coroutine elision.

**MSVC**
MSVC also supports coroutine elision. To enable it across separate `.cpp` files, you must compile with Whole Program Optimization (`/GL`) and link with Link-Time Code Generation (`/LTCG`). During the LTCG phase, the MSVC backend can see across the ABI boundaries, determine the frame sizes, and elide the `new` calls for nested `co_await` chains.

*Caveat for MSVC:* Historically, MSVC's optimizer has been slightly more conservative than Clang's regarding HALO. While VS 2022 has improved significantly, complex control flow or exceptions can sometimes cause MSVC to conservatively fall back to heap allocation even with WPO enabled.

### 2. Architectural Fallbacks (The "Safety Net")

Because relying entirely on compiler optimization passes for performance architecture can be brittle (a seemingly innocent code change can break the compiler's ability to prove strict lifetimes, causing a sudden performance regression), high-performance network loops rarely rely on HALO alone.

If you are writing a single-threaded event loop, you can guarantee allocation efficiency regardless of the ABI boundary or compiler heuristics by using **Custom Coroutine Allocators**.

C++20 coroutines allow you to overload `operator new` and `operator delete` on your specific `promise_type`. Because your event loop is driven by a single dedicated thread, you can implement a highly efficient, lock-free memory pool or arena allocator:

```cpp
struct MyTaskPromise {
    // ... promise interface methods ...

    void* operator new(std::size_t size) {
        // Allocate from a thread-local memory pool or arena 
        // specifically tuned for your event loop.
        return MyThreadLocalPool::allocate(size);
    }

    void operator delete(void* ptr, std::size_t size) {
        MyThreadLocalPool::deallocate(ptr, size);
    }
};
```
By supplying a custom allocator, you create a win-win scenario:
*   If the compiler (via LTO/WPO) successfully elides the allocation, your custom `operator new` is never called, and the frame is efficiently placed on the stack.
*   If the ABI boundary or complex branching defeats HALO, the fallback is a lightning-fast O(1) allocation from your thread-local pool rather than a global, mutex-locked `std::malloc`.

### Summary Recommendation for Your Migration

1.  **Use LTO/WPO:** Turn on `/GL` and `/LTCG` in MSVC (and `-flto` in Clang) for your release builds. This resolves the ABI chicken-and-egg problem and allows the compiler to perform HALO across your `.cpp` files.
2.  **Implement a custom allocator:** Overload `operator new` on your promise types using a thread-local memory pool. This ensures that even when the compiler fails to elide an allocation, the cost of spilling local variables across suspension points remains negligible compared to OS-level thread context switching.

## [2026-10-22] Memory pools

<query>

### User's query

Another question relating to this topic.  Let's say the protocol only supports one ‘message’ at a time, but each message is variable-length, so that the functions that parse the messages have to be coroutines that can suspend.  If the parser is coded in the traditional way as a manual state machine, without coroutines, one would essentially pre-allocate the required frame variables to retain, as member variables in the per-connection object/structure.  And with that no dynamic memory allocation is required to start parsing new messages.

So, it seems, to implement the same optimization with C++20 coroutines, a per-connection memory pool would be required.  Implementing custom memory pools in the codebase I'm working with is not ‘my cup of tea’ (I've done it many times elsewhere and the details are tricky enough, especially when the allocation size isn't fixed and known upfront), but I guess there's no way around that.  Do you know of good open-source examples out there to look at?  I want to see how this issue is handled in a “production-quality” codebase.
</query>

<response>

### AI's response: introduction

Yes, implementing a custom memory pool is the standard architectural solution when you need guaranteed, O(1) coroutine frame allocation per-connection and cannot rely entirely on compiler elision.

To see how this is handled in production, you don't need to guess. The C++20 standard anticipated this exact use case and built a specific mechanism for it: **Coroutine Argument Snooping**.

Here is how production-quality open-source codebases handle it, the C++20 mechanics behind it, and how you can avoid writing a tricky memory pool from scratch.

##### The C++20 Mechanism: Argument Snooping

In C++20, if you overload `operator new` on your coroutine's `promise_type`, the compiler will attempt to pass **the arguments of the coroutine function** directly into `operator new`.

This means if your parser coroutine takes a `Connection` object as its first argument, your custom `operator new` can intercept that object, access its per-connection memory pool, and allocate the frame without hitting the global heap.

```cpp
struct ParseTask {
    struct promise_type {
        // ... standard promise methods ...

        // 1. The compiler passes the coroutine arguments here!
        template <typename... Args>
        static void* operator new(std::size_t sz, Connection& conn, Args&&...) {
            // We need to store a pointer to the pool so operator delete can find it.
            // We allocate extra space for a pointer just behind the frame memory.
            std::size_t total_size = sz + sizeof(MemoryPool*);
            
            void* mem = conn.pool().allocate(total_size);
            
            // Store the pool pointer at the start of the block
            auto* pool_ptr = static_cast<MemoryPool**>(mem);
            *pool_ptr = &conn.pool();
            
            // Return the memory just AFTER our hidden pointer
            return pool_ptr + 1; 
        }

        // 2. operator delete does NOT receive the coroutine arguments, 
        // so we must recover the pool pointer we hid in operator new.
        static void operator delete(void* ptr, std::size_t sz) {
            // Step backwards to find our pool pointer
            auto* pool_ptr = static_cast<MemoryPool**>(ptr) - 1;
            MemoryPool* pool = *pool_ptr;
            
            // Free the memory back to the specific connection's pool
            pool->deallocate(pool_ptr, sz + sizeof(MemoryPool*));
        }
    };
};

// Usage: When this is called, ParseTask::promise_type::operator new 
// is automatically invoked with `conn` and `buffer`.
ParseTask parse_message(Connection& conn, std::span<const std::byte> buffer) {
    // ... co_await ...
}
```
*Note: The "hidden pointer" trick shown above is a staple in production C++20 coroutines because `operator delete` is called during frame destruction, at which point the original function arguments may no longer exist.*

##### Open-Source Codebases to Study

If you want to read how the industry leaders implement this, here are the three definitive open-source codebases to look at:

**1. Boost.Asio / Boost.Cobalt**
Boost.Asio provides an excellent production reference for network-bound coroutines (`asio::awaitable`). Asio heavily utilizes `asio::associated_allocator`. Instead of strictly binding the allocator to the connection object, Asio extracts the memory allocator from the executor (the event loop) or the completion token.
*   **What to search for in their repo:** Look up `boost::asio::recycling_allocator`. Asio uses a thread-local recycling cache that caches coroutine frames of similar sizes, making the allocation effectively free after the first run, without needing a strictly bounded per-connection pool.

**2. Meta's Folly (`folly::coro`)**
Authored in large part by Lewis Baker (the architect of much of the C++20 coroutine standard), Folly's coroutine library is as "production-quality" as it gets. Folly supports custom allocators via `std::allocator_arg_t`.
*   **What to search for in their repo:** Look at `folly::coro::Task` and `folly::SysArena`. Folly often defaults to using a fast thread-local cache for coroutine frames so that engineers don't have to manually pass connection arenas around, keeping the function signatures clean.

**3. Seastar (by ScyllaDB)**
Seastar takes a radically different approach that might appeal to you. It is a shared-nothing, thread-per-core asynchronous networking framework.
*   **What to search for in their repo:** Look at their custom memory allocator. Seastar completely replaces the global `std::malloc` and global `operator new` with a lock-free, thread-local slab allocator. Because their event loops are strictly pinned to a single CPU core, global heap allocation becomes an O(1) lock-free operation. In Seastar, you don't even write custom coroutine allocators; you just use standard `new`, and the framework's underlying slab allocator makes it as fast as a per-connection pool.

##### How to avoid writing your own pool

You mentioned that writing custom memory pools is not your cup of tea. Since you are using C++20, you don't have to. You can use the standard library's **Polymorphic Memory Resources (PMR)** (introduced in C++17).

Instead of writing a complex allocator, give each `Connection` object a `std::pmr::monotonic_buffer_resource`.

A monotonic buffer resource is a blazing-fast arena allocator. It doesn't track individual deallocations. It just bumps a pointer forward into a pre-allocated stack buffer until the connection drops or the message finishes parsing, at which point you call `.release()` to instantly free the entire arena in O(1) time.

```cpp
###include <memory_resource>

class Connection {
    // Pre-allocate a 4KB buffer for coroutine frames on the connection struct
    std::array<std::byte, 4096> frame_buffer;
    std::pmr::monotonic_buffer_resource arena;

public:
    Connection() : arena(frame_buffer.data(), frame_buffer.size()) {}
    std::pmr::memory_resource* memory_pool() { return &arena; }
    
    void reset_parser() {
        arena.release(); // Instantly reclaims all coroutine frame memory
    }
};
```
By combining C++20's argument snooping with C++17's `std::pmr::monotonic_buffer_resource`, you get the exact performance of a hand-rolled, zero-dynamic-allocation manual state machine, with only a dozen lines of infrastructure code.

### User's thoughts on the above response

The ‘arena’ is not so good as it is requires a known ‘reset’ point.  If it is called too early then memory corruption ensues.  What is really desired is a ‘memory pool’ that behaves like the stack, but with explicit allocation and de-allocation of variable-length items. Still, the code is probably subtle enough that it is best left as a much-later optimization, not as part of the initial work.
